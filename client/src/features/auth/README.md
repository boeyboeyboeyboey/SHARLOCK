# Browser account journey

## Presentation summary

- What it is: the browser side of accounts: `/register` (with email verification), `/login`, session restoration, logout and the pixel page wipes.
- Security concept: authentication and session management. Passwords are checked by the shared policy, sent once over the shared client, then cleared; the session is an HttpOnly server cookie, the CSRF token lives in memory only, and nothing sensitive reaches `localStorage`. Registration needs a six-digit email code before the first session. Course link: authentication and identity (06-authentication v2.pptx) and web security (11a, 12a decks) in the [course reference index](../../../../TASKS.md#course-reference-index).
- Using it: open `/register`, pick an avatar, enter email, username and password, then type the code printed in the server terminal (no real email is sent); use `/login` afterwards.
- Components: `LoginPage`/`RegisterPage`, `LoginForm`, `RegisterForm`, `VerifyEmailPanel`, `AvatarPicker`, `SessionNotice`; `store.js` (Pinia auth state), `api.js`, `guards.js`, `validation.js`.
- Data: the store keeps the safe user DTO, a memory-only CSRF token, the pending verification (restored from the server's pending session after a refresh) and why the last session ended; passwords are never stored.
- Status: see the AUTH-01-A/B and AUTH-03 records in [TASKS.md](../../../../TASKS.md).
- Limits: the verification code goes to the server terminal only; the E2E journey needs a replica-set test database; browser guards are UX controls, the server enforces access.

AUTH-01-B connects the approved backend account foundation to the shared student website. Registration, login, refresh restoration, logout, browser navigation checks and real account identity use the existing pixel theme. COH-01 adds the [class enrollment continuation](../cohorts/README.md).

## Student flow

- A signed-out visit to town, any game or The Sharlock Times opens sign-in. Arriving from another guarded page such as `/settings`, the page says "Sign in to open that page." (read from `route.redirectedFrom`, so the URL and the guard do not change); the town is the front door and gets no notice. About remains public. Profile and Progress remain readable shells with sign-in/create-account prompts.
- Registration collects email, username, password, matching confirmation and one of six capybara presets. Only email, username, password and avatar ID reach the server. Registration then swaps the card in place to **Check your email** (a refresh returns here, because the pending session is on the server; "Use a different email" ends it): six code boxes (auto-advance, Backspace steps back, arrow keys, paste, one-time-code autofill), a Confirm button enabled only when all six are filled, and a resend countdown. Confirming the code establishes the session and continues through any class invitation or one-time optional onboarding before town. This is a project demonstration: the code is printed in the **server terminal**, not emailed (see the [backend contract](../../../../server/src/modules/auth/README.md#email-verification)). Signing in to an account that never confirmed its email goes to the same code screen.
- Login uses email and password. Existing valid sessions restore after refresh; account forms continue through enrollment when needed, otherwise returning to town. Staff bypass student onboarding.
- Menu logout invalidates the current server session before returning to sign-in. Failed network logout retains the identity and offers retry. If the cached CSRF token is stale (for example the session cookie lapsed), logout refetches the token and retries once, then lands on sign-in; a second rejection keeps the identity.
- Expired sessions stop a pending browser activity request before dispatch and return to sign-in. **Any** 401 `AUTHENTICATION_REQUIRED` on a request made while signed in ends the session in the store and, on a page that requires an account, returns to `/login`; the sign-in page says "somewhere else" when the server reports a newer sign-in replaced the session (SESS-01), otherwise that the session ended. Returning to a tab rechecks the session, since an idle tab makes no requests; there is deliberately no timer, because each check counts as activity and would keep an idle session alive. Signed-out callers and failed sign-ins never trigger this, so a public page or the sign-in form cannot loop. No mutation is automatically replayed, with one exception: a sign-in or registration refused only because its short anonymous session lapsed (`CSRF_INVALID`) is resent once with a fresh token, since the server wrote nothing. Unavailable session checks block protected navigation/actions and show useful recovery feedback.
- Town, menu and Profile use the saved username/avatar. Saved game results, points and badges appear on the Profile and Learning progress pages; no sample rewards are attached to the real account.

Usernames accept 3–32 ASCII letters, digits, underscores or hyphens. New passwords require at least 12 well-formed Unicode code points (the server also enforces a maximum of 128, which the interface does not advertise), at least one uppercase letter and one punctuation/symbol character. The sign-in form only asks for a password and states no length rule. Login preserves older passwords without applying new composition rules.

The class data/access foundation and COH-01 enrollment are connected. Invitations are stripped from the address before restoration, carried as a short-lived hash in the existing server session, and submitted only after account access. Onboarding completion is server-owned and applies once to existing/new students; Skip preserves personal play. If class setup fails after successful account access, Continue retries enrollment lookup without sending credentials again. [Admin](../admin/README.md) and [activation](../activation/README.md) provide staff setup; the router admits only a freshly verified administrator to `/admin`.

## Components and state

`pages/LoginPage.vue` and `RegisterPage.vue` own local submit state and compose `LoginForm`/`RegisterForm`. Forms hold passwords locally, clear them on success/unmount, disable editing while pending, and focus a textual error summary. `AvatarPicker` uses labeled native radio inputs. `SessionNotice` accepts `{ message, pending }` and emits `retry`; it and `AvatarPicker` (which accepts a `heading`) import their own stylesheets, so they look right on pages that do not load `auth.css`. Both pages end with a plain-text `auth-field-hint` line, "Instructor? Ask your administrator for an activation link.", pointing instructors to the admin-issued activation flow (no self-service instructor sign-up). The sign-in page also says what Sharlock is and where a forgotten password goes: there is no self-service reset, so it names the instructor or school administrator who can send a link.

**Page wipes.** Arriving on one of the main tabs, or opening a game, from a different page plays an 8-bit screen wipe that belongs to that destination: after signing in or up, clicking a sidebar tab, the logo or a game's Enter activity, using Back, or returning from a game. Each wipe has three beats: the screen is covered (the route changes underneath), held covered so the destination card can be read, then cleared. Every wipe lasts about 1.6 s from the first block to the last: 0.42 s to cover, a 0.73 s hold, 0.42 s to clear (`WIPE_COVER_MS`, `WIPE_HOLD_MS`). The card appears early enough to be readable for about 1.0 s, and clicking, tapping or pressing a key during the hold skips the rest of it.

Blocks on a 16 × 10 grid switch on in hard one-millisecond steps (never a fade), then switch off in the same order:

| Destination        | Pattern                                                                     | Colour         | Emoji and label                 |
| ------------------ | --------------------------------------------------------------------------- | -------------- | ------------------------------- |
| Town map           | diagonal staircase from the top-left                                        | dark green     | 🗺️ Entering Sharlock Town…      |
| Detective profile  | interlaced shutters (even rows sweep left to right, odd rows right to left) | slate          | 🔍 Opening your detective desk… |
| Your classes       | checkerboard, dark squares first                                            | gold           | 🎒 Finding your classes…        |
| Cohort leaderboard | checkerboard                                                                | gold           | 🏆 Checking the rankings…       |
| About Sharlock     | rings spreading outward from the centre                                     | capybara brown | 🐹 Meeting Sharlock…            |
| Sign in            | bars rising from the bottom                                                 | blue           | 🔑 Heading to the sign-in desk… |
| Create account     | diagonal staircase from the top-left                                        | blue           | 📝 Opening the sign-up desk…    |
| Join a class       | rings spreading outward from the centre                                     | green          | 🔖 Finding your class…          |
| Class management   | interlaced shutters                                                         | purple         | 📋 Opening the class register…  |
| Admin workspace    | bars rising from the bottom                                                 | grey           | 🛡️ Entering the control room…   |

Settings and Discoveries have no wipe of their own: an overlay without a section counts as town, so opening or closing one plays nothing. `/progress` redirects to the Progress tab of `/profile`, which is the same section as the Profile tab.

**Game doors.** Opening any game plays a pair of pixel-art double doors instead of blocks. The leaves slide shut in stepped frames, the card is held on them like a sign (for example "🕵️ Entering LLM Social Engineering Simulator…"), then they swing open in perspective onto the game. Each game has its own door colour and emoji (`GAME_DOORS` in `pixel-wipe.js`: 💻 green CLI Cyber Defender, 🎣 blue Phishing Post-Mortem, 🕹️ plum SQL Injection Arcade, 🕵️ purple Social Engineering Simulator, 🏢 slate Clearance Tower); the label comes from the catalog name, and a game with no entry gets a plain wooden 🚪 door, so adding a game needs no change here. Going from a game back to town plays the town wipe. The landing page `/` is now the [3D hub](../../../../README.md#using-the-app) and the pixel Sharlock Town is the 2D mode option; "town" in the wipe names is the destination label, not a route change.

`pixel-wipe.js` holds the tab table (`WIPE_SECTIONS`), the pattern functions (`WIPE_PATTERNS`, each written in any unit and scaled so every pattern takes the same time) and `sectionConfig`, and exports `installPageWipes(router)`, a `beforeResolve` hook installed in `main.js`; adding a tab is one table entry. It runs after the account guard, so a signed-out visitor sent to sign-in gets the sign-in wipe (blue bars and a key) rather than the wipe for the page they asked for. It does not play on the first page load, for moves within a tab or within the same game (including the newspaper dialog on town), when going to a page with no wipe, or for reduced motion. Moving between two destinations plays the new one's wipe. `components/PixelWipe.vue` draws it and is mounted once in `App.vue` so it survives the page change; `pixel-wipe.css` styles it. The panel also carries the destination's emoji, redrawn as an 8-bit sprite by `components/PixelEmoji.vue`: the system emoji is painted onto a 32 × 32 canvas, flattened to a limited palette with hard edges and scaled up with nearest-neighbour, so it matches the pixel theme instead of showing as a smooth system glyph. It hops in a two-frame bob and is hidden from assistive technology. The overlay blocks clicks while it plays, caps its wait on animation frames so a background tab cannot hold it on screen, and returns to idle on a cancelled or failed navigation, a thrown guard, or an eight-second watchdog. A game's How to play dialog (`components/common/HowToPlayDialog.vue`) opens only once the wipe is back to idle, because a modal dialog draws in the top layer above the doors (FIX-06).

`RegisterForm.vue` validates live with the same shared rules the server enforces: a field warns once it has been left with something in it (or a submit was attempted), then follows what is typed, so its warning disappears the moment the value is valid. The top banner appears only after a submit attempt and also clears when every field is fixed; errors reported by the server clear when that field is edited. A warning raised by pressing the mouse or a finger on another control waits until the press is released, because a warning that appears mid-click pushes the page down and the click misses its target (this broke the browser test when first added). Tab skips the Show/Hide buttons (Alt+S toggles visibility from inside a password field).

`components/VerifyEmailPanel.vue` accepts `{ verification, pending, error }` and emits `submit(code)`, `resend` and `cancel`; `AuthSteps.vue` accepts `{ current, total }` and draws the square step indicator. Both pages swap form, code screen and signed-in view inside a `Transition` whose frames are stepped in `auth.css` (8 frames in, 4 out, so it reads as pixel motion, not lag). Motion is removed for reduced-motion users. Only the form and code screen sit inside the `Transition`; the signed-in view is outside it, because signing in navigates away at once and an `out-in` transition holding a not-yet-mounted view crashes Vue when its page is unmounted mid-swap. The pages derive "signed in" from the store, so nothing re-renders the form between the code screen and signing in. The code boxes use a 1 : 1.618 width-to-height ratio.

`store.js` owns the shared Pinia status, the `pendingVerification` details (kept in memory; a refresh restores them from `GET /auth/session`, and cancelling waits for the server to end the pending session, keeping the code screen with a message if it could not), `sessionEnd` (why the last signed-in session ended: `elsewhere`, `expired` or null), safe user DTO, memory-only CSRF token and safe request feedback. It deduplicates restoration/bootstrap and uses operation generations to keep stale responses from undoing a newer login/logout. Passwords and confirmation never enter store state or browser storage. `api.js` reuses the shared Axios cookie client and maps only approved public errors. `validation.js` and `avatars.js` reuse the backend's existing public, data-only policy/preset definitions; session, hashing, models and secrets stay out of the client bundle.

`guards.js` provides the injected router guard, the browser activity request check, the one response interceptor that treats a 401 as the end of the session, and the recheck on returning to a tab. A 401 ends the session only for a request sent under the current `sessionGeneration()`, so a reply from before a sign-in or sign-out changes nothing; someone who never signed in is never told a session expired, and a deliberate sign-out during a recheck is not reported as expiry. Background checks (the return recheck, presence) call `restoreSession({ force: true, quiet: true })`, which raises no alert when the server cannot be reached. `LoginPage` honours `?returnTo=` only for a game's own path, after any class invitation or onboarding. `main.js` installs them after Pinia and before initial navigation. Protected News/game requests await the current server session before dispatch, while auth and public health requests bypass that check to prevent recursion. Initial activation and class-link entries clear their private fragments before restoration. The existing game/news wrappers and engines remain unchanged.

## Boundaries and design

These browser checks are user experience controls, not direct-API authorization. Existing game APIs still use their interim unsaved resource contracts. Server capabilities, cohort permissions and game-resource ownership require their later approved foundation tasks; do not claim those guarantees from this UI.

`auth.css` is limited to auth feature roots and consumes the existing cream/earthy-green tokens, Pixelify Sans headings with DotGothic16 body text, square controls and hard shadows. Navbar/layout reuse the retained smooth 3D logo, mobile offcanvas and focus handling. Town camera, gestures, audio and game-local styles are preserved. See [DESIGN.md](../../../../DESIGN.md).

Run `pnpm dev`, open `/register`, select an avatar and create an account; then check town/Profile, refresh, logout and sign-in. About is available without an account. Use a Mongo connection as described in the root setup; this slice adds no dependency or configuration change.
