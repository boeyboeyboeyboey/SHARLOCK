# Admin workspace

## Presentation summary

- What it is: the `/admin` workspace for administrators to create institutions and classes, provision instructors and other administrators, assign instructors to classes, manage account status, read audit events and start student password recovery.
- Security concept: role-based access control and least privilege with accountable administration. The route requires a freshly verified admin; the server re-checks role on every call, never accepts a submitted role, and writes metadata-only audit events. Course link: access control (07-access-control.pptx) and authentication (06-authentication v2.pptx) in the [course reference index](../../../../TASKS.md#course-reference-index).
- Using it: sign in as an administrator, open Admin workspace (four tabs: Institutions & classes, Instructors, Accounts, Audit log; the choice lives in `?tab=`), create an institution then a class, open the Instructors tab, open "Add staff", use "Provision an instructor", copy the one-time activation link from the dialog and deliver it privately, then "Edit assignments" and "Save assignments" once the instructor has activated. "Add staff" also has "Provision an administrator" (ADMIN-03), which reuses the form and the one-time link dialog and creates a disabled admin account that finishes setup at `/activate-account`. Each save confirms in a status line that stays on screen.
- Components: `pages/AdminPage.vue` plus `InstitutionCohortForm`, `InstructorProvisionForm`, `AssignmentEditor`, `ActivationLinkDialog`, `DeleteAccountDialog`, `AccountStatusPanel`, `PendingAdministratorsPanel` and `AuditEventsPanel`; `api.js` wraps the admin endpoints.
- Data: sends only `{ name, slug }`, `{ institutionId, name, term }`, `{ email, username, avatarId }` and `{ cohortIds, expectedRevision }`; edits use `expectedRevision` to reject stale writes. Activation links are shown once and cleared on close. Account deletion (ADMIN-04) sends `{ confirmUsername, password, reasonCategory, reasonNote?, expectedRevision }` and clears the password after each attempt.
- Status: see the ADMIN-01-A, REC-01-A and LOG-01-A records in [TASKS.md](../../../../TASKS.md).
- Limits: needs transaction-capable MongoDB; existing users are never promoted; a new administrator exists only after an existing administrator issues the link and it is redeemed; the Instructors tab lists pending administrators (ADMIN-05) and pending instructors with Reissue link and Cancel, and a 404 means the account is no longer pending; no student enrolment or learning dashboard here (see the cohorts and class-results modules); no demo fixtures.

The `/admin` utility page replaces the earlier preview in place. It uses the shared admin API and the existing `PortalLayout`, pixel tokens, `PixelIcon`, and `AvatarPicker`; router registration, account guards, and the role-aware navigation entry are shared integration points.

## Administrator flow

Administrator provisioning (ADMIN-03) sends the same `{ email, username, avatarId }` to `POST /admin/administrators` through `createAdministrator`; the account is created disabled and the link is shown in the existing dialog. The account-status panel still lists only pure students and instructors, so administrators are never disabled here.

A tab row under the hero switches between **Institutions & classes**, **Instructors** (provisioning, assignments), **Accounts** (account controls and student password recovery) and **Audit log**. The selected tab is the `?tab=` query value (`institutions`, `instructors`, `accounts`, `audit`); a missing or unknown value falls back to `institutions`, and selecting a tab uses `router.replace` so history is not filled. The tabs follow the leaderboard pattern: `role="tablist"`, a roving `tabindex`, ArrowLeft/ArrowRight wrapping and Home/End. Panels are hidden with `v-show`, so form drafts survive tab switches; each list loads on mount and rereads when its tab opens, so a change made on one tab shows on the next. The activation-link dialog sits outside the tabs. Delete account uses `--alert-danger` with white text, Enable account uses `--accent-primary` and Disable account the plain style, set apart from Delete; all keep their text labels. Below 640px each account row is a card, and the table keeps explicit roles for assistive technology.

The page requests institutions, classes, and instructors with bounded pages. An administrator creates an institution, selects it to create a class, provisions a separate disabled instructor, and privately delivers the single-use activation link. Disabled instructors can receive a replacement link; active instructors can be assigned to active classes.

Institution and class creation send only `{ name, slug }` and `{ institutionId, name, term }`. Existing institutions can be edited by name or deactivated/reactivated; their IDs and slugs remain fixed. Existing classes can be edited by name/term or deactivated/reactivated; their IDs and parent institutions remain fixed. Edits use an `expectedRevision` and stale revisions require a reload. A class can be reactivated only while its institution is active; an institution can be deactivated only when all its classes are inactive. Class deactivation preserves memberships, instructor assignments, and history, but revokes its invitation; reactivation requires a new invitation. Reactivating an institution does not change class statuses.

Instructor provisioning sends only `{ email, username, avatarId }`; confirmation and passwords are never collected here. The Instructors tab lists pending administrators and instructors first, with the provisioning forms in a collapsed "Add staff" section below. Each instructor row shows the assigned classes; "Edit assignments" opens the checklist for one instructor at a time, and its count says whether the selection is saved. Assignment updates send `{ cohortIds, expectedRevision }`. New assignment choices require an active class in an active institution. Previously assigned inactive classes remain visible as read-only retained assignments and stay in the save payload. A stale assignment revision preserves the local draft and waits for the administrator to reload before another save. Lists use 20 items by default; assignment options request at most 50 classes at a time.

The read-only audit viewer filters by event type and optional browser-local date bounds. Leaving either date empty lets the server apply its current 90-day window on each request. Results show the event, outcome and time to the second, who did it to whom and the class, using names the server looks up for each page; identifiers are available on expansion, and a deleted record simply has no name. There is no export. Pagination requests 25 rows at a time (up to 50).

Account controls list only pure student or instructor accounts, show the email, and support role/status filters and a username or email prefix search. Administrators and mixed-role accounts are excluded. Administrators can enable or disable students and disable active instructors; a disabled instructor must use the existing private activation-link flow to regain access. Disabling an account preserves memberships/assignments while revoking its active sessions and outstanding activation/recovery links. This page does not edit roles, passwords, or credentials.

Delete account (ADMIN-04): pure-student rows in the Accounts tab get a danger "Delete account" button that opens `DeleteAccountDialog` (native `<dialog>`, focus returns to the row button on Cancel/Escape). The dialog warns that the action is permanent, explains that students with saved results are anonymised (results kept, never on leaderboards) and others are removed completely, and requires the typed username (case-insensitive), a reason (Wrong name, Duplicate account, Student request, Left school, Other) and the administrator's password; Other also needs a 10-500 character note ("Don't include names or emails."). Server field errors and generic errors show inline and keep the dialog open. On success the panel shows "Account deleted." or "Account anonymised; saved results kept." and reloads the list. A stale revision closes the dialog, reloads the list and says so beside the row, since the old revision could never succeed on retry. Instructors keep Disable only. The Audit log filter "Account deleted" requests the last 180 days when no start date is set and shows the outcome, reason and note on each row; the maximum audit range is now 180 days.

Each mutation obtains a fresh CSRF token and is sent once. Safe API errors use fixed local messages; raw response text is not rendered, and a 409 names its cause (slug taken, class exists, account exists, classes still active, nothing changed). Server field errors for the create and edit forms appear beside their inputs through `aria-describedby`. A 401 has no message of its own: the shared handler in `features/auth/guards.js` ends the session and returns to sign-in. Disabling an account, cancelling a pending account and deactivating a class or institution each ask first in an inline `InlineConfirm` step (from the cohorts feature), not a native dialog. Focus moves to the list heading after an action removes the control that had it. If a link fails validation after the server has already committed, the list reloads and the message says to reissue it (`ADMIN_LINK_NOT_SHOWN`). The activation URL is validated as a same-origin `/activate-account` link with a 32-byte base64url token in its fragment and no query string. It exists only in component memory and the open dialog; closing the dialog removes it from the page. The copy action runs only from an explicit button press.

`api.js` owns the shared Axios calls and safe error mapping. `AdminPage.vue` owns request lifetimes, paginated lists, mutation state, and the one-time link. `InstitutionCohortForm`, `InstructorProvisionForm`, and `AssignmentEditor` keep their editable inputs local and emit only the approved fields. `AuditEventsPanel` and `AccountStatusPanel` own their focused filters, result states, and controls. `ActivationLinkDialog` presents the private link with a copy-now notice and names the account it belongs to; closing it or pressing Escape before copying asks first, and focus returns to the control that opened it. `admin.css` scopes every rule under `.admin-workspace`.

Focused mounted tests live in `__tests__/admin.test.js`. The real admin-to-instructor journey is in [`tests/e2e/admin-workspace.spec.js`](../../../../tests/e2e/admin-workspace.spec.js), and layout at 375 and 1200px with the failure paths in [`tests/e2e/staff-pages.spec.js`](../../../../tests/e2e/staff-pages.spec.js); both use the guarded synthetic admin fixture. The workspace operates on the normal database when used normally; test fixtures are restricted to disposable `_test` databases.
