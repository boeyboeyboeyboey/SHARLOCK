# Course alignment

## Purpose

This page keeps the implementation aligned with what WAD2 taught and with the project brief. It records where our testing and state handling match the slides, where they differ on purpose, and which gaps are still open. It does not assign tasks; task status lives only in [TASKS.md](../TASKS.md).

Sources:

- [project_brief_and_rubric.pdf](../documentation/project_brief_and_rubric.pdf). Minimum Requirements (p3): "Your solution should include (at least End-to-End) Testing of the application's core features". The README must say how to test, and the presentation must describe how the features are tested. Testing is 10% of the final deliverables. The rubric (p9) rewards main user journeys covered, repeatable and stable tests, stable selectors, a clear test structure, clear README instructions and an understanding of testing concepts.
- The four decks in `documentation/WAD2 Course Details/`: `(Week 10a) Intro to Testing.pptx`, `(Week 10b) Component and Integration Testing.pptx`, `(Week 10c) E2E Testing.pptx` and `Week11Slides.pptx`.

The decks set no project requirement: no coverage threshold and no per-feature test count. The requirement comes from the brief and rubric. Slide numbers below are written S17 for slide 17 of the named deck.

## Testing: taught versus ours

| Topic                    | Taught (slides)                                                                                                                                                                          | Ours                                                                                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit runner              | Vitest (10a S17-18)                                                                                                                                                                      | Vitest 5 with jsdom; `vitest.config.js` defines the client, server and integration projects                                                                                                                 |
| Component tests          | A component test is the unit of one component (10b S3); Vue Test Utils `mount`, text, `find`, `trigger`, props, `emitted`, `$nextTick` (10b S30)                                         | `@vue/test-utils` 2.5 with the same API                                                                                                                                                                     |
| Stubs                    | `global.stubs` (10b S4, S7-9)                                                                                                                                                            | `global.stubs` where needed; `vi.mock` at module boundaries (API client, router, timers), which the slides do not cover                                                                                     |
| Integration              | Several components mounted together without stubs (10b S15-16)                                                                                                                           | Same idea for components, plus a server layer: supertest against the Express app and a real disposable MongoDB started by `scripts/run-with-test-db.mjs`. The slides do not use "integration" in this sense |
| End to end               | The whole system from the user's view (10a S7, 10c S3); Playwright via `pnpm create playwright`, recorder, `getByRole`/`getByText`, auto-waiting, `await` every action (10c S4, S7, S13) | Playwright 1.63; `playwright.config.js` runs every spec on `mobile-chromium` (375x667) and `desktop-chromium` (1440x900) against its own API and client                                                     |
| What to test             | Behaviour, not implementation (10b S13-14). Worth testing: props to render, conditional render, interactions, emitted events, computed values, states (10b S10-11)                       | Same rule in [agents.md](../agents.md) section 9                                                                                                                                                            |
| What not to test         | Every tag, CSS classes, exact HTML structure, framework behaviour (10b S12)                                                                                                              | Same rule; see gap 6 for older tests that still select by class                                                                                                                                             |
| File names and locations | `*.spec.js` and `src/components/__tests__` (10a S18, 10b S20-22); `tests/` for Playwright (10c S7)                                                                                       | Vitest files are `*.test.js`, co-located in `__tests__/`; server tests live in `server/tests/{unit,integration}/<module>/`; Playwright specs are `tests/e2e/*.spec.js`                                      |

Verdict: the tools and concepts match the course. The differences are file naming and the extra server-integration layer. Both are kept on purpose: renaming about 100 files adds churn without earning marks, and the API layer is where our authorization rules are proven.

## State (Week 11)

| Topic                | Taught (Week11Slides.pptx)                                                                                                                                                          | Ours                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stateful logic       | Composables hold stateful logic (S3-4); component-local `ref` (S5)                                                                                                                  | Games and pages keep state in feature composables and local refs                                                                                            |
| Sharing state        | Prop drilling is the problem (S6); Pinia is the central source of truth with setup stores: `ref` is state, `computed` is a getter, a function is an action, return all (S7, S16-25) | One Pinia setup store, `auth`, at `client/src/features/auth/store.js`. Feature-folder rules put stores with their feature, so `client/src/stores/` is empty |
| When to use a store  | Only for data used in many places, not page-local visibility (S8); stores are optional (S8)                                                                                         | Same. No provide/inject and no event bus                                                                                                                    |
| Naming               | Stores in `@/stores/`, named `useXStore` (S17, S19)                                                                                                                                 | `useXStore` naming kept; the location follows the feature folder                                                                                            |
| Route guards         | Guards are UX only; the backend enforces auth (S48)                                                                                                                                 | Same: guards redirect, and every API route checks the session server-side                                                                                   |
| Persistence and auth | Exercises 3-4 (S42-45) persist the login in `localStorage` and send a Bearer token                                                                                                  | Deliberate deviation, see below                                                                                                                             |

`localStorage` is used only for hub and town preferences such as `sharlock.townMode`, never for authentication.

Deliberate deviation: the Week 11 exercises store a token in `localStorage` and send it as a Bearer header. We use an HttpOnly, Mongo-backed session cookie plus an in-memory CSRF token ([agents.md](../agents.md) section 6, OWASP session management guidance), because a token in `localStorage` is readable by any injected script. Do not change this to match the slides.

## Presentation note

- Describe three levels: Vitest unit and component tests, API integration tests against a real disposable MongoDB, and Playwright end-to-end journeys.
- Say what the tools are and why: Vitest and Vue Test Utils (taught in Week 10), supertest for the API, Playwright on a phone-sized and a desktop viewport.
- Quote approximate counts and say they are approximate: about 49 client test files, about 50 server unit files, about 22 integration files and about 16 E2E specs, each run on two viewports.
- Mention the repeatability measures: each run creates and removes its own `_test` database, `pnpm test:e2e` starts its own API and client, and specs use role, label or `data-testid` selectors with auto-waiting instead of fixed sleeps.
