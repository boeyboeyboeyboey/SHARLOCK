Read this alongside [TASKS.md](TASKS.md) and [agents.md](agents.md) before changing the portal or adding a game. No shared visual style is currently selected: the earlier pixel-art pivot (UI-04) and cyberpunk directions are not a binding future style, and games choose their own design. The accessibility and component contracts below stay in force, and shared-UI style changes are proposed to Boey before they are applied. The 3D hub (HUB-01 to HUB-04, see TASKS.md) is the default on `/`; the pixel town is its 2D mode. Keep the open-world town, direct building selection and accessible navigation. This file is the design contract for every teammate and AI agent adding shared UI. Individual games have the explicit design exception below; Task 3 hover-card refinement has been skipped.

## Rules for new pages and features

Treat the current implementation as the reference, not a loose mood board. Every new shared page, form, dialog, loading/error/empty state and navigation control must extend this scheme. Do not reintroduce the retired pastel/Inter design, rounded card system or a replacement shared theme through a feature implementation. The existing admin/log-content exception above remains valid.

| Reuse / inspect                                                                     | Responsibility                                                                                                                                                                  |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client/src/assets/styles/main.css`                                                 | Exact shared palette, Pixelify Sans, square forms/buttons, hard shadows and focus styles. Use these variables/classes rather than copying colour literals or redefining tokens. |
| `client/src/layouts/PortalLayout.vue` and `client/src/components/portal/Navbar.vue` | Shared shell, retained 3D logo, title visibility, navigation, mobile offcanvas and focus handling. Do not build a competing header.                                             |
| `client/src/components/portal/`                                                     | Existing profile, progress, trophy, tip and connection-state components; reuse the appropriate component and its contract. Sample data remains labelled.                        |
| `client/src/assets/styles/town.css` and `client/src/components/town/PixelIcon.vue`  | Town layout/controls and original shared pixel icon vocabulary. Do not load a different icon style for shared UI.                                                               |
| `client/src/data/gameCatalog.js` and `client/src/features/legacy-town/`             | Single building registration, shared metadata card, existing pan/zoom camera and audio. Follow the registration procedure below instead of duplicating them.                    |

Before coding an approved UI task, identify whether it is a shared page, permitted admin/log content or a game module. State which existing components/tokens will be reused and how new styles are contained. A generic Bootstrap component must receive the existing shared styling; framework defaults are not a new visual direction.

Include a focused user question-and-answer checkpoint about feature design and implementation in the plan, then ask follow-ups when a new material ambiguity appears during implementation. See [agents.md §2.D](agents.md#d-clarify-and-confirm-before-coding); clarification does not replace explicit scope approval.

For readability conventions, use [CODE_STYLE.md](CODE_STYLE.md). Bootstrap utilities are preferred for ordinary grid, layout and spacing when they clarify the markup; this does not replace shared design tokens, town styling, or intentionally custom and isolated game themes.

During review, compare shared surfaces with the current landing, profile and town; check 375/576/768/992/1200/1440px, breakpoint edges and landscape, keyboard/touch access, visible focus and no page-wide horizontal scrolling. Visit another shared page after leaving a game to check for style leakage. Do not redesign shared components as an incidental part of a game or feature; a requested change to the shared design needs its own explicit scope.

### How to play dialog

Games show their guide through `client/src/components/common/HowToPlayDialog.vue` (HOW-01), not a custom modal. It is a native `<dialog>` with a step caption, step dots, Previous/Next, a "What you'll learn" line, rules, controls, a "Don't show again" checkbox saved to the account, and a "Start playing" button. The game supplies the animated mini-UI through the `scene` slot, built in code (no images, GIF or video). The scene advances every 4 seconds with a **Pause animation** toggle (`aria-pressed`, WCAG 2.2.2); under `prefers-reduced-motion` it starts paused and shows static steps. A game themes the dialog from its own root with `--game-howto-*` variables (`surface`, `scene`, `edge`, `ink`, `muted`, `soft`, `bar`, `bar-ink`, `bad`, `bad-soft`, `font`), which fall back to the shared tokens; never style it from `:root` or another module.

### Game design freedom and isolation

Game screens have freedom over **layout, typography, artwork and controls**, and **colour starts from the town's palette**. A learner who walks from the town into a game should recognise the same place, so a game builds its palette from the shared tokens in `client/src/assets/styles/main.css` (`--bg-primary`, `--surface`, `--accent-primary`, `--accent-secondary`, `--border-strong`, `--text-main`), mapped onto local `--game-*` variables on the game's root class. Games are **not required to use the hub's pixel font, square controls or pixel-art treatment**, and keeping realistic or custom type is encouraged where the content needs it. Deviating from the town palette is fine when it is absolutely necessary for the game's theme (see Colour exceptions). Describe the palette mapping, any deviation and any typography choice in the game implementation plan without changing the shared design contract.

**Colour exceptions.** A game may depart from the town palette when its theme absolutely needs it, and that is acceptable. The CLI Cyber Defender's hacker terminal (black with green and amber) is the accepted example: a terminal that looked like the town would lose the theme. Agents must not recolour an accepted themed game to the town palette unless its owner asks. A deviation should be limited to the simulated screen itself, with the frame around it (back link, title, buttons that leave the game) in town colours where practical. Write the reason in the game plan, and meet contrast (text 4.5:1, focus indicators and UI outlines 3:1). Personal preference and a real product's brand colours are not reasons: keep the realism in layout and type and use town colours (Phishing and Social Engineering moved from blue and purple accents to the town palette on 14 October 2026 for this reason).

The Phishing Post-Mortem is the first game to use this freedom. Its triage screen shows each email as a realistic mail card (sender, reply-to, link, attachment, QR and request line as tappable parts) with a system font stack and the town's earthy green and cream (palette unified with the town on 14 October 2026), because a spoofed sender only teaches when the email looks like a real one. The earlier SHARMAIL inbox layout was replaced by the PHISH-01 triage run on 28 October 2026. Every rule lives under `.phish-game` in `client/src/games/phishing-post-mortem/phish.css` with `--game-*` variables on that wrapper, and it copies no real product's branding, wordmark or icons. CLI Cyber Defender is the accepted colour exception, kept at the team's request on 14 October 2026: an original green/amber-on-black terminal set in Silkscreen (headings, stats and stamps) and Azeret Mono (body and terminal text), loaded from Google Fonts with a system monospace fallback, contained under `.cli-game` in `client/src/games/cli-cyber-defender/cli.css`. It lays out with the Bootstrap grid and re-themes Bootstrap buttons, badges and progress bars through their `--bs-*` variables inside that wrapper; reduced motion turns off its animations, flash/shake feedback, confetti and scanline overlay. Its line icons are original game-local SVGs that always sit beside a text label. Its optional sound effects are generated in the browser, start off on every visit and are never remembered, consistent with the soundtrack rules below.

Current mapping for Phishing Post-Mortem (realistic screen): `--game-accent` is `#50634d` (the town's `--border-strong`), `--game-accent-soft` is `#e3eacb` (`--accent-secondary`), the title bar uses `--game-bar` `#a8c98a` (`--accent-primary`) with `--game-bar-ink` `#25331f`, `--game-bg` is `#eef3e6` and surfaces stay white. Correct and mistaken calls in the triage feedback use `--game-good`/`--game-good-soft` and `--game-bad`/`--game-bad-soft` and always carry a text label. Success, warning and error colours keep their own hues and always sit beside a text label, because the green accent and the success green are close in lightness. The Social Engineering Simulator follows the hub's full pixel look (changed on 15 October 2026 at Eric's request, since its chat has no spoof-detection clues that a pixel font could hide): `--game-font` is the hub's body font `var(--font-body)` (DotGothic16) and headings use `--game-heading-font` `var(--font-pixel)` (FONT-07), corners are square, panels use a 3px `--game-edge` (`#50634d`) border with a hard offset shadow, controls use a 2px edge with a 2px shadow that presses in, surfaces are the town's cream (`#fff8df`) on the town's sky green (`#dfead6`), and the chat bubbles are cream (colleague) and `--game-bar` green (learner). Clearance Tower (15 October 2026, Russell's choice) uses the same light town palette and the same body/heading font split as the Social Engineering tokens (FONT-06), with square controls, hard shadows and a plain numeral font for scores, all under `.clearance-game` in `client/src/games/clearance-tower/clearance.css`; it has no colour exception. `client/src/games/__tests__/game-palette.test.js` checks the contrast and, for Social Engineering, the body/heading fonts and square corners. An all-pixel treatment that also restyles content is still parked for Phishing; see `docs/superpowers/specs/2026-10-14-unified-game-theme-design.md`.

Keep game components/styles under `client/src/games/<game-id>/`. Use Vue `<style scoped>` or a module-specific root class, game-specific control classes and local variables such as `--game-*`. Assign game fonts and variables on that wrapper. Do not write game overrides against `:root`, `html`, `body`, `.portal-shell`, the navbar, shared root tokens or another module; avoid unscoped/deep selectors that escape the game. A component imported by a game must follow the same isolation rule.

The game's **town building, label, shared metadata card, shared navbar and any shared profile/progress/result UI** continue to use the shared pixel scheme. Custom gameplay controls/feedback inside the game may use their own layout and type, in the town's colours unless a documented colour exception applies. Its theme does not waive keyboard/touch access, readable controls, reduced-motion handling, 375px-and-up responsiveness, or shared authentication and result contracts. Never solve a layout problem by shrinking a desktop game board into an unreadable mobile image.

## Proportion and the golden ratio

New pages, panels and game screens should size their major regions with the golden ratio, φ ≈ 1.618, so layouts feel balanced without a new visual style. This is a **proportion guideline**, not a new palette, font or component. It does not authorize redesigning an existing shared page; apply it to new work and to surfaces already being changed in an approved task. Accessibility always wins: the 18px shared body size, the 44px touch targets, contrast and reflow rules in this document are never reduced to hit a ratio.

- **Two-region layouts.** Split the width 1 : 1.618 (about 38.2% to 61.8%), with the secondary region (controls, navigation, inspector, list) as the narrow side and the primary content (chat, board, reading area) as the wide side. In CSS use `grid-template-columns: minmax(0, 1fr) minmax(0, 1.618fr)`, or the reverse. Collapse to a single stacked column below 768px instead of squeezing both regions.
- **Content width.** For a screen with two regions, a 1100px maximum is a good fit. Text-only reading areas keep their existing line-length limit of about 62–66ch.
- **Spacing scale.** Use steps that grow by about φ: 0.5rem, 0.8rem, 1.3rem, 2.1rem, 3.4rem (the Fibonacci series in tenths of a rem). Use the smaller steps for gaps inside a control or card, the middle steps for padding, and the larger steps between sections. The existing 3px and 4px hard borders and shadows are not part of this scale.
- **Type scale.** Where a page needs several heading sizes, step them by √φ ≈ 1.272 from the 1rem base (1rem, 1.272rem, 1.618rem, 2.058rem) rather than choosing sizes ad hoc. Pixelify Sans weights stay 700 for headings; DotGothic16 body text stays 400.
- **Vertical rhythm.** Where a region is split top-to-bottom, give the primary region about 1.618 times the height of the secondary one (for example the chat thread against its composer).
- **Prefer shared tokens.** Keep ratios in the owning module's local variables (`--game-*` for a game). Do not add φ tokens to `main.css` or `town.css` without a separately approved scope, because those files are shared.

**Current use.** The Social Engineering Simulator conversation (changed on 15 October 2026 at Eric's request) splits the decision rail and the chat 1 : 1.618 from 768px upward and widens its chat view to 1100px (`.is-wide` in `client/src/games/social-engineering-simulator/sim.css`); below 768px it stacks. On bigger windows the whole conversation screen, including the debrief, scales up in proportion with CSS `zoom`: `--soc-scale` in `sim.css` is the largest factor that still fits the window, never below 1 and never above 1.8, so the text, cards and spacing grow together; a browser without `zoom` and the CSS math functions skips the block and keeps the fixed size. ## Town interaction and responsiveness

The rules in this section describe the 2D pixel town, which is the 2D mode on `/` and the no-WebGL fallback. These are the 2D mode controls; the 3D hub controls are in [README "Using the app"](README.md#using-the-app) and [client/src/features/hub/README.md](client/src/features/hub/README.md).

**Every game is available from the start.** There are no linear locks, unlock messages, grayscale unavailable nodes, or completion requirements. Difficulty and background knowledge help learners choose; neither gates access. Future server authentication and cohort permissions still apply independently of this learning sequence.

- `Dashboard.vue` displays the town introduction and `TownMap.vue`. The town has no navbar or sidebar: see **Site menu and overlays** below (UX-01).
- The town world is **1120 × 800 CSS pixels**, defined by `TOWN_SIZE` in `client/src/data/gameCatalog.js`. `Dashboard.vue` applies the `.town-canvas` boundary (maximum 1126px including its 3px borders). `TownMap.vue` uses **`@panzoom/panzoom` 4.6.2** for drag, pinch, focal zoom and containment; the viewport uses `overflow: clip` so transformed scenery cannot expand the page or introduce native focus scrolling. Keep the package instance and camera state local and dispose listeners/observers on departure. If the world changes size, update the dashboard canvas limit too.
- Buildings are semantic buttons in a list. **Hover or keyboard focus** shows details; **click/tap or Enter/Space** keeps the card open and moves focus to its title for preview activities. The approved newsstand exception opens the Times directly; hover/focus and Jump to retain its shared metadata card. A separate action in the card enters the activity. Escape or Close dismisses it and restores focus to the selected building.
- Every metadata card contains **Game Name**, **Description**, **Difficulty (exactly 1–3 stars)** and **Background Knowledge Needed** as a short list. A screen-reader label announces the numeric star rating. Cards are clamped to the whole map panel and may overlap the toolbar and controls, so they keep their full height; they scroll internally only when taller than the browser window itself. Touch users receive the same information as mouse users.
- **Drag/swipe** within the map to pan; pinch to zoom. The **Jump to** select, **− / + / Reset view** buttons and a zoom percentage share one toolbar row above the map, outside the transformed world; the Sound button is in the floating controls and the layout hint paragraph is visually hidden (it stays as the viewport's description). Start at **100%**. The steps are fit, 50, 75, 90, 100, 125, 150, 175 and 200%, where **fit** is the scale at which the whole 1120 × 800 town fits the viewport (recomputed on mount and resize; steps below it are skipped, and a world smaller than the viewport is centred rather than left with an empty margin). The − button, wheel and pinch stop at fit, + stops at 200%, and limit buttons are disabled. Reset restores the initial camera; no camera preference persists. Pan/zoom is immediate, without motion tweening.
- Focus the viewport and use **arrow keys** to pan, **+ / −** to zoom and **0** to reset. The wheel/trackpad pans; Shift-wheel pans horizontally and Ctrl/Command-wheel zooms. **Jump to** centers any building and opens its card; keyboard focus also brings buildings into view. Touch users can scroll the page outside the canvas.
- Ignore the click generated after a drag/pinch; a fresh click/tap or Enter/Space still pins the card. Keep camera controls and metadata outside the scaled layer so text/control sizes remain stable. Card coordinates update after camera transforms and resizing. Preserve the pointer-focus protection for first taps.
- Offcanvas must trap focus, close with Escape/backdrop/Close, and restore focus. Resizing to desktop must remove the mobile backdrop and scroll lock.
- `GlobalProgressBar.vue` and `TrophyCase.vue` remain available on pixel-styled profile/progress screens. Progress is informational and never controls building availability. Trophy badges wrap using flexbox.

## Fit-to-window layout

Added at Eric's request on 14 October 2026 after scrolling made the town and games hard to read on a laptop-height window. The town and every state of the playable games (briefing, play, debrief) fit one window without page scroll; the target is **1280 × 720** and the rule applies from **768px wide and 600px tall**. Below those sizes pages scroll normally. Long prose pages (About, Profile) are not fitted.

- **Shared sizing token.** `--shell-chrome` in `client/src/assets/styles/main.css` is the height taken by the header, main padding and footer (236px by default). `.portal-main:has(.case-preview, .is-fitted)` trims the padding and sets it to 176px; the town shell sets 140px in `town.css`. A fitted page sizes itself with `height: calc(100dvh - var(--shell-chrome))` and a `min-height` so it never collapses.
- **Game opt-in.** A game root adds an `is-fitted` class and keeps every rule scoped under its own root class in its own stylesheet, as the game-isolation rules above require. Social Engineering and CLI Cyber Defender use it. The Phishing triage run (PHISH-01) no longer does; its single-column card scrolls with the page.
- **One flexible region.** The region that can grow absorbs spare height and scrolls inside itself: the chat thread, terminal output, briefing and debrief panels, the debrief panels. Headers, score HUDs, composers, decision buttons and the verdict bar keep their size, so the primary action is never pushed below the fold.
- **Town.** The map fills the remaining height, with the intro, toolbar, zoom controls and footnote compacted. The zoom range is fit to 200% (see above), so at 720px tall the map pans inside a shorter frame, and its `ResizeObserver` recomputes fit and re-clamps the camera.
- **Activity card.** The card is no longer capped to the map frame. See the card rule in Town interaction and responsiveness.
- **Debriefs.** Social Engineering uses two columns from 900px wide. CLI keeps the result summary and actions visible and scrolls the detail inside the panel.
- **Scroll panes and hidden text.** An absolutely positioned visually-hidden element inside a scrolling pane stretches the page unless the pane is `position: relative`. Set it on any scrolling game pane for this reason.
- **Phishing triage bar.** `TriageStatusBar.vue` shows the clock, score, streak and mistakes above the email card, with **Report** and **Trust** under it. After Report the buttons give way to a "Tap what gave it away" bar with Cancel; Escape also cancels.
- **Checking it.** Measure `document.documentElement.scrollHeight <= window.innerHeight` for every town and game state at 1280 × 720 and again at 1440 × 900, then open a building card and each game's longest state. A temporary Playwright height check was used for the first pass and then removed; add an equivalent check when a game is added.
- **Open decision.** Social Engineering is close to pass/fail but shows a score out of 100. An outcome-first debrief with the number as a secondary line was proposed on 14 October 2026 and deferred, so nothing here changes the scoring display yet.

The visible pixel **Sound off / Sound on** button sits in the map toolbar's corner (2D); the 3D hub has its own Sound on/off button in its HUD row (AUDIO-03), sharing the same session mute.
