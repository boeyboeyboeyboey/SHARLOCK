### Planning and teaching before implementation

**Always default to producing a technical plan and assume the user will implement it by hand. Never create or edit code unless the user explicitly gives permission for you to make the specific code changes.**

This includes application code, tests, scripts, schemas, configuration, scaffolding and generated scene/model code. Plan approval alone, tool write access, a failed test or a request for advice is not permission to edit code. Do not make changes indirectly through formatters, generators, dependency commands or subagents. All implementation instructions elsewhere in this file are conditional on explicit code-edit permission. Permission already given remains valid only for its exact, unchanged scope.

- **Develop the idea together.** Turn a goal, broad idea or the team's concept art into a feasible proposal. Suggest suitable technologies, explain tradeoffs and challenge weak assumptions. Revise the plan through discussion rather than treating the first suggestion as settled.
- **Agree the next step.** Produce a technical plan for hand implementation: intended behaviour, approach, exact files, interfaces, dependencies, security boundaries and focused checks. Identify any proposed documentation changes. Ask about material uncertainties and discuss the plan. Do not silently choose agent implementation. Only an explicit instruction for the agent to perform the specified code edits authorises implementation; approval of the plan alone does not. If that permission and the required plan approval already exist for the same scope, do not ask again.
- **Explain difficult bugs before changing code.** The intended workflow is human debugging first, with AI help when the team is stuck. Build on their reported attempts and ask only for missing details needed to understand the issue. Explain the reproduction, likely cause, a focused fix and a way to check it. Default to a fix plan the team can apply by hand. Do not patch code unless the user explicitly authorises you to apply that fix.
- **Keep generated work specific.** The user may delegate tests, scene/model code based on their own drawings, scripts, content, assets, presentation tasks or bounded code refinements. These examples are not blanket permission to generate or replace a feature. Preserve the team's supplied ideas and reference art, and record the actual tools, sources and licences used.
- **Keep the work bounded.** Inspect Git status and diffs before edits, use only approved paths and preserve teammates' and uncommitted work. Do not add unrelated cleanup, dependencies or features. Commits, pushes and other changes to branches or history need explicit authorisation for the action; do not create or switch branches without approval.
- **Teach from evidence.** Explain CS440 concepts simply using the supplied course sources below, then help the team translate them into game rules. Verify time-sensitive security guidance with primary sources. Do not claim model output or benchmark scores guarantee accuracy, secure code or current best practice.

## 2. Mandatory feature-selection decision tree

This workflow applies to every feature proposal, whether the user suggests it or it extends an existing module. A blueprint, star rating, empty directory or earlier stage approval does not authorize implementation.

### A. Detect collisions

Search by task ID, feature name, concept, alternate names, routes, components, schemas, services, fixtures, tests and relevant Git history. Check current files, the user's current instructions, available coordination information and available branch/PR information. A matching feature-specific prototype or preview is partial implementation. A generic empty directory alone is not implementation. An active claim is a coordination conflict even when its code is not present locally.

Report which worktrees, branches or remote work were not available; a clean local tree cannot prove teammates have no changes. Never assume a feature is available without checking its implementation, ownership and the user's current instructions.

### B. Stop on existing work

**If the chosen feature has any partial or complete implementation, the agent is strictly forbidden from touching, overwriting, refactoring, deleting, replacing or continuing that feature's existing code.** Stop immediately, identify the conflicting files/tasks/branches, explain what exists and ask the user to choose another feature or get the owner's agreement to extend theirs.

Do not silently collaborate, take over unfinished code or treat an existing contributor's absence as consent. Do not evade the guardrail by renaming the same feature, cloning its implementation or starting a competing version. Previous general statements allowing shared ownership are not permission to edit a colliding feature under this kickoff workflow. Preserve the work while the user selects another task.

### C. Route the user

Offer exactly these two selection paths:

1. Extend an existing module, with its owner's agreement.
2. Propose a brand-new custom feature, then inspect it for collisions too.

If the proposed work overlaps existing work, ownership or dependencies, explain that and offer a new feature or an independent prerequisite. Never begin implementation with no selected task.

### D. Clarify and confirm before coding

For every feature or separately approved feature-change plan, include a focused question-and-answer checkpoint about the user journey, design and intended behavior, and the technical implementation. Ask about areas that could materially shape the plan: objective, difficulty, background knowledge, interaction loop, scoring, feedback, replay, failures, mobile/keyboard/touch behavior, components and props/emits, local/shared state, API payloads, validation, schemas, integration boundaries, external services and acceptance checks. Build on answers already given; do not repeat settled questions.

Recommend concrete defaults and explain tradeoffs. Summarize settled decisions in the technical plan and identify unresolved questions. Present the final plan and **wait for explicit user approval before writing a single line of implementation code**. Silence is not agreement. During implementation, ask follow-up questions when a new ambiguity or discovery could materially affect user experience, behavior, data/security, architecture, dependencies, acceptance or approved scope. Pause only the affected work for a required answer or approval; continue independent work already in the approved scope. Clarification does not replace scope approval or contributor agreement. Do not repeatedly ask approval for an unchanged approved scope. Before approval, do not scaffold files or install dependencies. Stop at the technical plan by default. Implement only after the user explicitly authorises the agent to make the specified code edits and the required plan/owner approvals are in place. Retain that permission for its exact scope without repeatedly asking for the same approval.

### E. Recheck, record and implement

Immediately before any explicitly permitted edits, reread the approved plan and permissions and inspect Git/files for changes since planning. New overlap returns to the collision guardrail. Summarise the contributor, scope, branch, affected paths, dependencies, collision evidence and next action in the conversation or a plan file the user requested. Do not automatically create or modify project logs. State material AI contributions truthfully: planning, explanations, generated code/assets, tests, debugging or review. Do not relabel earlier work or treat newly added rules as evidence of past practice.

Use lowercase `<task-id>-<description>` for new branches; omit the `codex/` prefix as Boey requested on 13 October 2026. Preserve historical branch references. Reuse shared infrastructure through established interfaces. Only the additive catalog/router registrations explicitly included in the approved plan may be made; preserve other entries and behavior. A missing shared contract requires a separately agreed prerequisite task, not a second implementation inside a game.

For readability maintenance of existing code, inspect one bounded area read-only, propose up to three useful changes with unchanged behavior and narrow checks, then wait for the owner’s agreement and explicit scope approval. This does not authorize a new-feature collision, whole-project rewrite, or edits to Social's separately owned `llm/` engine without that contributor's agreement. Preserve uncommitted work and inspect the latest agreed project instructions on `main` before completing or publishing an older branch; never blindly pull, checkout, reset, or overwrite it.

## 5. Data and permission boundaries

- Institutions contain cohorts. A student has at most one active or pending class membership at a time (COH-04, Boey, 30 October 2026, with team consent; earlier extra memberships are kept, not migrated); instructors may have multiple assignments. Membership states are pending, active and removed.
- Registration creates only a student. A submitted role, user ID, cohort ID, institution, score or achievement is never proof of authorization.
- An administrator may provision another administrator only through the audited one-time activation link (ADMIN-03, Boey, 27 October 2026); an existing account is never promoted and the role comes from the route, never the request body. While that administrator has never activated, another administrator may reissue the link or cancel the pending account, both audited (ADMIN-05, Boey, 28 October 2026).
- Cohort entry requires an active approved membership. New requests must reflect removals/account changes; revoke or refresh stale sessions.
- Instructors may inspect only their assigned cohorts' activity. Administrators may inspect learning activity across cohorts. Staff gameplay does not expand teaching permissions.
- Every attempt has one server-validated cohort or personal context, immutable after creation. A student's other cohort memberships do not widen access to that attempt.
- Scope every query/mutation and nested-resource lookup to the authenticated actor. Explicitly serialize only caller-appropriate fields.
- Profile updates allow only approved username/avatar fields; never mass-assign bodies into user, membership or result documents. A per-game How to play dismissal list (`howToPlayDismissed`) is set only through its own validated endpoint, `PUT /api/me/how-to-play/:gameId` (HOW-01, approved by Boey on 27 October 2026), never through the profile PATCH.
- Wharf presence (MP-01) shows only the viewer's class: the server places a student in their class; an assigned instructor or an administrator joins a class they choose and is labelled as staff. It sends username, preset avatar, public outfit and position under a per-connection id; never emails, user IDs or rosters. The 2D town shares this presence with 2D positions; each mode draws only its own peers while the online list counts both. Recheck the session and membership while connected and disconnect on sign-out or removal.
- Leaderboards expose only authorized cohort rankings with username, preset avatar and score/rank. Rank only completed class-context attempts by students with current active membership; exclude staff and personal practice; never mix games or rulesets. A game with a timed competitive mode ranks only its timed runs; a game without one may rank untimed class-context best scores, labelled as practice best scores (team decision recorded by Boey on 27 October 2026, replacing the earlier exclusion of all untimed training). An all-time view may also show each ranked student's completed-play count, total points and best score for that game and ruleset (Boey, 27 October 2026, with team agreement); never emails, user IDs, attempt details or rosters.
- Tests must request another cohort's, student's and attempt's IDs directly, including pending/removed membership cases.

## 6. Authentication, recovery and secrets

Use maintained Argon2id password hashing with per-password salts and a work factor checked against primary guidance during implementation. Never store recoverable passwords or return password hashes in responses, exports, logs or administrator views.

Use Mongo-backed server sessions with cookie identifiers, `HttpOnly`, `SameSite`, bounded idle/absolute lifetime and rotation/revocation. An account holds one active session: a new login ends its other sessions and their wharf presence, and the signed-out tab says so (SESS-01, Boey, 31 October 2026; the newest login wins so a stale or stolen session can never lock the owner out). Restrict the HTTP cookie exception to explicit localhost development. Do not put auth tokens in browser local storage. Apply CSRF and expected-origin checks to state-changing requests, including login/logout; GET must not mutate state.

Validate allowed fields, types, IDs, enums and bounds. Construct Mongo filters from validated values rather than accepting arbitrary operators. Rate-limit login, recovery, enrollment and expensive endpoints; bound bodies, upstream time and generated output. Use generic authentication/recovery failures where needed to prevent enumeration, with useful next steps and no stack/configuration leaks.

The approved REC-01-B scope verifies identity through a school channel outside the app. All issuers with the admin role use the admin area, including admin/instructor accounts; administrators with `admin:recovery:manage` may help any active pure student, with or without classes. Instructor roster controls are for issuers with the instructor role and no admin role; each target must have active membership in an active class/institution assigned to that instructor. Staff and dual-role targets are excluded; emergency recovery is deferred. Recheck issuer, target, assignment and membership at issuance and redemption. After all eligibility and revision guards pass, count the attempt against the student quota even if later token, audit or commit work fails; transaction callback retries count the same request once, while unauthorized or ineligible requests do not charge the shared student bucket. Generate a random, expiring, single-use token; store only its hash and reveal the link once to authorized staff for private delivery. The student chooses the password. Consume the token atomically, revoke sessions and require normal login. Audit actor, outcome and time without secrets. User-facing password guidance says “at least 12 characters” plus the existing uppercase and punctuation/symbol requirements; never display “12–128 characters.” The backend enforces its 128-character maximum. Check the current implementation before describing readiness or verification.

Never print, overwrite or commit root `.env` or `server/.env`. The backend reads `process.env.MONGO_URI` with shell → root `.env` → server defaults precedence. Preserve the team's `.env.example`. Keep credentials, cookies, tokens and connection strings out of client code, `VITE_*`, screenshots, notes and logs. Keep database binaries, dependencies and generated artifacts out of Git.

Primary references: [password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Verify implementation-specific recommendations when choosing dependencies and policy values.

## 7. Scoring and synthetic exercises

The server creates attempts, selects player/context/ruleset, checks actions and calculates scores. Enforce ownership, lifecycle, deadlines, bounded action history, concurrency checks and idempotent completion. Keep answers/private state out of public bundles/responses; never accept browser totals or achievement grants. Saved outcomes are performance evidence, not scientifically validated mastery.

- Botnet Tag positions, tags and patch-station puzzles are validated and decided on the server; puzzle answers stay server-private and a snapshot carries only the caller's own puzzle.
- CLI commands operate on fictional state only; never execute a shell or change a real host/network.
- Social-engineering chat uses synthetic training codes, server-owned prompts, bounded transcripts and no tools/account access. Prompt text is not a security boundary; the server determines outcomes. Keep real secrets out of prompts/logs.
- Phishing email/link content is inert synthetic text with no clickable links. The server generates each round from a private seed and checks the report/trust call and selected part against the private answer.
- SQL-injection puzzles use a bounded teaching parser and never execute vulnerable database queries or grant real administrator access.
- Regex evaluation runs within bounded workers with termination deadlines, not unbounded `.test()` loops on the UI/server event loop. Explain false positives and limitations.
- News uses an allowlisted upstream, bounded requests and labeled caching. Escape external text, avoid untrusted `v-html`, validate link protocols and do not proxy arbitrary URLs.
