# Authentication foundation

This backend module provides student registration, account sign-in, session restoration and sign-out. AUTH-01-B connects the [browser account journey](../../../../client/src/features/auth/README.md). DATA-01-A/AUTH-02-A reuses this session runtime for authenticated class reads. Existing game APIs retain their unsaved contracts; authentication alone does not grant cohort access or saved attempt ownership.

## Request flow

`GET /api/auth/csrf` creates or reuses a short-lived anonymous Mongo session and returns a synchronizer token. Registration, login and logout require an exact trusted `Origin` (or the same origin parsed from `Referer` when `Origin` is absent) and the token in `X-CSRF-Token`. Registration creates only a student and, with AUTH-03, ends at a pending-verification session; confirming the emailed code and login rotate the session ID, persist the new session, and return a fresh token. Every auth request rechecks an authenticated session's idle and absolute bounds plus the current account status and auth version. An expired authenticated session may obtain a fresh anonymous token through a new bootstrap request; disabled or version-stale sessions are invalidated. `GET /api/auth/me` returns only the current safe user DTO. `POST /api/auth/logout` destroys the current session.

## HTTP contract

All auth responses use `Cache-Control: no-store`. The browser sends the session cookie automatically; no auth token belongs in browser local storage. Each mutation requires `X-CSRF-Token` plus the configured client origin through `Origin`, or a same-origin `Referer` when `Origin` is absent. A missing or `null` origin does not authorize a mutation. Unknown body or query fields are rejected.

| Endpoint                                | Exact JSON body                           | Success                                                   |
| --------------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| `GET /api/auth/csrf`                    | none                                      | 200 `{ csrfToken }`                                       |
| `POST /api/auth/register`               | `{ email, username, password, avatarId }` | 202 `{ verification, csrfToken }`, not signed in yet      |
| `POST /api/auth/verify-email`           | `{ code }`                                | 201 `{ user, csrfToken }`, signed in                      |
| `POST /api/auth/verify-email/resend`    | empty or `{}`                             | 202 `{ verification }`                                    |
| `POST /api/auth/login`                  | `{ identifier, password }`                | 200 `{ user, csrfToken }`, or 202 `{ verification, csrfToken }` when the email is unconfirmed |
| `GET /api/auth/me`                      | none                                      | 200 `{ user }`, or 401 when unauthenticated               |
| `POST /api/auth/logout`                 | empty or `{}`                             | 204, current session invalidated                          |
| `POST /api/auth/class-invitation`       | `{ code }`                                | 204, hash retained in the current session for ten minutes |
| `POST /api/auth/class-invitation/clear` | `{}`                                      | 204, invitation draft cleared                             |

Email is trimmed, lowercased ASCII, syntactically validated and at most 254 characters. Username is trimmed, 3–32 ASCII letters, digits, underscores or hyphens; uniqueness is case-insensitive. New passwords are unchanged, well-formed Unicode strings of 12–128 code points with at least one Unicode uppercase letter and one punctuation/symbol character. Whitespace does not satisfy the special-character requirement. Login checks only encoding/length, preserving older composition-free passwords. These are Boey's approved policy changes of 15 October 2026. Registration accepts only the six IDs in [avatars.js](avatars.js); submitted roles, IDs, memberships, scores and other account fields are rejected.

Safe failures use `{ error: { code, message, fieldErrors? }, requestId }`. Login takes an email address or a username in `identifier` (an `@` selects email; both are matched case-insensitively), and still accepts the older `{ email, password }` body. Invalid credentials use the same 401 error for an unknown email or username, a wrong password and disabled accounts. Duplicate email or username returns a generic 409 without identifying the conflicting index. Invalid input is 400, rejected origin/CSRF is 403, rate limits are 429 with `Retry-After`, and exhausted password-operation capacity is 503. Registration success is returned only after the session save completes. If account creation succeeds but session storage later fails, the account remains available for a normal login retry; no account is deleted as a rollback.

## Storage and private fields

`User` is bound to the existing Mongoose connection and the `users` collection. Storage initialization creates the collection, unique normalized-email and normalized-username indexes, the `auth_sessions` collection and its `expires` TTL index. It does not drop collections, synchronize indexes destructively or seed records. Password hashes use Argon2id with a random salt and the approved memory/time/parallelism settings. Registration always writes `globalRoles: ['student']`.

The only user DTO contains `id`, `email`, `username`, `avatarId` and `globalRoles`. Password hashes, auth versions, account status, timestamps and session fields stay server-side. Six preset IDs map to `/images/avatars/<id>.png`; their image files are generated and tracked separately.

Sessions use `express-session` with the maintained `connect-mongo` store over the existing Mongo client. Only the actual session object created by a successful rotation may use connect-mongo's new-session upsert; later saves and idle touches conditionally update an existing, unexpired document without upsert. A touch after concurrent logout is a no-op, so it cannot restore the deleted ID. `GET /api/auth/me` returns 401 without destroying a valid anonymous session, allowing an invitation draft to survive the browser's session check before login. Expired anonymous sessions and invalid signed-in sessions are destroyed and cleared. The server checks expiry and account status/version on every authenticated auth request; MongoDB TTL cleanup is housekeeping rather than an authorization check. Cookies are HttpOnly, SameSite=Lax, scoped to `/api`, and Secure except for validated loopback development/test origins. The session adapter never closes the shared Mongo client.

## Limits

Password operations are Argon2id at 19 MiB, two iterations and one lane, with two process-wide operations allowed at once and no waiting queue. IP limits cover CSRF bootstrap, registration, login and activation (10 activation requests per 15 minutes). The CSRF bootstrap limit (300 per 15 minutes, `CSRF_BOOTSTRAP_LIMIT`) counts only requests that create or replace a session; a live session that already holds a token reuses it without spending the budget (AUTH-05). The per-IP sign-in limit (30 per 15 minutes) counts only failed sign-ins, so successful sign-ins from a shared address such as a classroom do not block each other (AUTH-06). Registration allows 30 accounts per hour per IP (`REGISTRATION_LIMIT`), enough for one class signing up together on a shared address (AUTH-06). A separate HMAC-keyed account/IP counter (the matched account's email, or the typed identifier when none matches, so email and username attempts share one budget) records only failed credential checks and expires after fifteen minutes; raw addresses and credentials are not used as limiter keys or logged.

Instructor activation is mounted at `POST /api/auth/activate-account` through the same origin/CSRF/session runtime; [recovery](../recovery/README.md) owns its transaction. [Admin](../admin/README.md) owns institution/class/instructor management. [Cohorts](../cohorts/README.md) owns enrollment and onboarding. General password recovery, account profile changes and persistent learning records remain pending. Sign-up [email verification](#email-verification) is implemented as AUTH-03. The current game APIs remain available under their existing contracts until separately approved integration.

Invitation capture requires the existing session, origin and CSRF protections, with a combined 30 capture/clear requests per fifteen minutes per IP. It validates code shape without revealing class existence to anonymous callers. Only a SHA-256 hash and ten-minute expiry enter session storage. Successful registration/login carries that allowlisted draft through session rotation without extending its lifetime; the public user DTO and credential payloads are unchanged. Logout destroys it with the session. Enrollment checks the current invitation record after authentication; a draft grants no membership authority.

## Email verification

AUTH-03 adds a six-digit confirmation step between registration and the first signed-in session. This is a project demonstration: **no real email is sent and no provider, credential or paid service is used.** The code is a `crypto.randomInt` value printed by the console mailer (`mailer.js`) to the server terminal as `[mail:dev] Verification code for <email>: <code>`. A real provider would replace only that one-method adapter. Browser tests run the server with `NODE_ENV=test` and `TEST_MAIL_OUTBOX`, which swaps in a file mailer; nothing else selects it.

- **Registration** creates the student with a pending `emailVerification` state and returns 202. The browser holds only an anonymous session that remembers the waiting account (`pendingVerificationUserId`, 30 minutes, longer than the code so an expired code can be resent). No authenticated session exists until the code is confirmed. A pending class-invitation draft is carried through confirmation.
- **Code rules** (`verification.js`): 6 digits, valid 10 minutes, stored only as an HMAC-SHA256 of the account id and code keyed by the session secret, compared in constant time. An attempt is reserved atomically before comparing, so parallel guesses all count; 5 wrong guesses lock the code until a new one is requested. Resend waits 30 seconds, allows 5 sends per hour and replaces the stored code with fresh attempts. A failed send does not start the cooldown.
- **Sign-in** of an unconfirmed account with the correct password returns 202 and sends a code instead of starting a session; wrong passwords still return the generic 401. `findActiveSessionUser` also refuses unconfirmed accounts.
- **Existing accounts count as verified.** The pending state is the only marker, so every account created earlier, by the admin tool or by activation needs no migration. `authService.register` is unchanged and still creates a verified account for those internal callers.
- **Reclaiming an address:** a new registration may replace an unconfirmed account only after its code has expired. Replacing a live one would let anyone swap the password under someone who is still confirming.
- Failures use `VERIFICATION_CODE_INVALID`, `VERIFICATION_CODE_EXPIRED`, `VERIFICATION_ATTEMPTS_EXCEEDED` and `VERIFICATION_NOT_PENDING`; resend limits use the shared 429. Verification requests share a 30-per-15-minutes IP limit.

## Reusable protected-request boundary

`createAuthRouter` returns `requireSession`, an array using the same session middleware/store and current-account lookup as the auth routes. Class, audit and admin routes reuse it. It sets no-store, checks idle/absolute expiry and current account status/authVersion, and supplies the server-derived `response.locals.authUser`. Invalid sessions are destroyed and receive a safe 401; no second session store or browser role claim is introduced. It also returns `requireMutation`, the existing origin/CSRF pair, for authenticated admin writes. Health, News and game routes retain their existing behavior.

The [class foundation](../cohorts/README.md) adds relationship and parent-status checks through shared permission/context services. Session identity is separate from class authority. Future mutations must also reuse CSRF/origin protection, and future attempts must persist their validated immutable context.

## Policy sources and verification boundary

The chosen Argon2id factors match the minimum configuration in [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), checked on 14 October 2026. Server-side idle/absolute expiry and session-ID rotation follow [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html); thirty idle minutes and eight absolute hours are this project's approved policy values. Synchronizer tokens and exact origin checks follow [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Auth unit tests cover input boundaries, salted hashing, bounded password work, failed-login limits and deterministic save/touch after revocation. Auth API integration tests cover registration, rotation, safe responses, duplicate creation, source/token checks, expiry, account invalidation and same-user session isolation against the guarded disposable `_test` database. These checks do not establish browser account UX, recovery, cohort permissions or saved game ownership.
