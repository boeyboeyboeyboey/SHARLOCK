# Cohort data and enrollment

The cohort module owns enrollment policy, the EnrollmentCode schema, strict request parsing and cohort enrollment routes. Existing Institution, Cohort, Membership and InstructorAssignment models use the application's Mongoose connection. `initializeCohortStorage` initializes only feature indexes, without seeding, dropping or synchronizing collections.

`GET /api/me/memberships?page=&limit=` returns only the signed-in actor's rows, including pending and removed entries, with the nullable decision label. `GET /api/me/teaching-assignments?page=&limit=` returns active assignments only to instructors and administrators. Both responses include bounded page metadata and explicit cohort/institution names and statuses. Missing parent records remain visible with null names and `unavailable` statuses; these read DTOs do not grant access.

The host app supplies shared session and mutation middleware and mounts the router at `/api`; this module does not create another session runtime. State-changing calls require the existing CSRF token and expected-origin checks. Enrollment and staff lists return `Cache-Control: no-store`; errors use the safe `{ error, requestId }` shape. Per-user and per-IP in-memory limits cover join requests, code issuance and other staff writes; `router.dispose()` shuts them down.

Students read `GET /api/me/enrollment` for onboarding state and whether a captured invitation is available. `PATCH /api/me/enrollment/onboarding` completes onboarding idempotently. `POST /api/cohorts/join-requests` accepts exactly `{ code }` or `{ invitation: true }`; successful joins consume a pending invitation session value. Duplicate pending/active requests to the same class are idempotent, while a removed membership can request again. COH-04: a student holds at most one active or pending membership; a join request to a different class, or approval of a pending request while the student holds another active or pending class, is refused with 409 `COHORT_ALREADY_IN_CLASS`, checked inside the same transaction. Staff are not limited and existing extra memberships are left untouched. `GET /api/cohorts/managed` lists cohorts available to the current instructor or administrator. `GET /api/cohorts/:cohortId/memberships?status=pending&page=&limit=` returns the scoped roster; staff can filter pending, active or removed members. `PATCH /api/cohorts/:cohortId/memberships/:membershipId` accepts `{ status, expectedRevision }` for approve, decline or removal transitions.

`GET /api/cohorts/:cohortId/enrollment-codes` reads current metadata. `POST` on that path accepts `{ expectedRevision }`, rotates the code and returns the raw code and one-time invitation URL. `DELETE /api/cohorts/:cohortId/enrollment-codes/:codeId` revokes it with the expected revision. Codes use 16 characters from an unambiguous 32-character alphabet, display in four-character groups, expire after seven days and are stored only as SHA-256 hashes. The one-per-cohort record is retained after expiry/revocation so revisions cannot reset. Transactional use-count fencing serializes joins against code replacement/revocation, and typed audit events are written in the same transaction as each successful change.

`createPermissionService` exports `resolveActor`, `requireCapability` and `listEligibleCohorts`. It supports `cohort:play`, `cohort:teach` and `cohort:review`: students need an active membership, staff need an active assignment, and administrators need an active cohort and institution. All active users may use personal context. Inactive or missing cohort/institution records are denied. `createContextService` exports `resolveAttemptContext` and `listEligibleContexts`; the latter returns `{ personal, cohorts, page, total }`, where `total` counts eligible cohorts. These checks resolve current permissions but do not establish persisted attempt ownership or immutable attempt context.

`parseRequestedContext` validates the exact requested personal/cohort context shape. It only normalizes the request; permission services recheck current membership, assignment, account status and cohort/institution status before any activity uses that context. Enrollment does not let clients choose a user or cohort identity. Current account, role, parent status and teaching scope are rechecked for mutations, and explicit DTOs prevent unrelated identities or code hashes from being returned.

## API response and policy bounds

Self-service lists return `{ memberships, page, total }` or `{ assignments, page, total }`; membership rows add nullable `decision` to the existing DTO. Staff roster rows contain only membership ID, username, email, preset avatar ID, status, decision, revision and request time. Lists default to 20, cap at 50 and page through 10,000. Unknown/repeated/object query values reject with a safe 400. Missing/expired/revoked sessions receive 401. Unsupported capabilities receive 403; absent or out-of-scope class requests use a generic 404. Request IDs accompany errors.

Shared schemas use active/inactive institution and cohort status, pending/active/removed membership status, and active/removed assignment status. Membership decision and revision fields preserve legacy records as null/zero. Names are trimmed and bounded to 100 characters, term to 50, and normalized lowercase institution slug to 3–64. Unique indexes protect slug, institution/name/term, user/cohort pairs and the single enrollment code per cohort.

The separation of identity and access follows the distinction in the supplied [07-access-control.pptx](../../../../documentation/CS440%20%28Cybersecurity%20Fundamentals%29%20Course%20Details/07-access-control.pptx), slides 4 and 6. The multi-class/assignment policy is a team design choice. Fresh checks and deny-by-default follow [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), reviewed 14 October 2026.

## Verification boundary

Enrollment policy/model units cover code normalization, exact inputs, bounds, expiry and indexes. Guarded replica-set enrollment integration covers invitation rotation/consumption, onboarding, duplicate and rejoin behavior, scoped roster decisions, stale writes, code rotation/revocation/expiry races, CSRF/origin and audit rollback. Existing foundation, auth and audit regression suites are the compatibility checks. The integration harness uses only a disposable `_test` database. No normal database or provider operation is part of verification.
