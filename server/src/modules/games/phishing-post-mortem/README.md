# Phishing Post-Mortem - server module

Three rulesets share the game ID `phishing-post-mortem`. `phish-4` is the current triage run. `phish-3` is the same run with the old maximum and `phish-2` is the earlier inbox investigation; both stay registered but not current so saved results and unfinished runs still read. The private answers never leave this directory.

## Request and data flow

```
client -> shared Axios client (baseURL /api)
  -> POST /api/games/phishing-post-mortem/attempts   (shared attempts router; body { context })
  -> POST /api/attempts/:id/actions                  (type triage-call)
  -> POST /api/attempts/:id/complete
  -> triage/ruleset.js    stored state, deadline, public state, summary
  -> triage/policy.js     constants, action allowlist, typed TriageError
  -> triage/scoring.js    judgeCall, streak and mistake tally, topic breakdown
  -> triage/generator/    seeded email generator (index, pools, random, templates, tricks)
```

This module adds no routes. `attempts/production-registry.js` registers `triageRuleset` (current), `triageLegacyRuleset` (phish-3, `current: false`) and `phishingRuleset` (phish-2, `current: false`). Ownership, context (personal or cohort) and ranking come from the shared attempts and leaderboards modules (see `server/src/modules/attempts/README.md`).

## phish-4 contract

- **Ruleset:** `phish-4`, generator `triage-2`, `competitive: true`, `maxActions` 60, `maxScore` is `PAR_SCORE`, 1,000. Rules are the same as `phish-3` (`maxScore` 6,610 from `maxTimedScore()`: 60 rounds, each a phish with its tell found, on a perfect streak, which no run reaches).
- **Par:** computed with the real generator and scoring over 5,000 seeds per row, flawless play with every tell found: 12 emails 580 to 840 (median 690, ceiling 850); 15 emails, 12 s each, 850 to 1,160 (median 990, 50% reach 1,000); 16 emails, 11 s each, 950 to 1,270 (98% reach 1,000); 17 emails, 10.6 s each, 1,030 to 1,380 (all reach 1,000). `summarize` and the public `score` both stop at 1,000. There is one maximum per ruleset, so personal practice cannot reach it: a flawless run earns about 69 and at most 85 Progress points, and no Perfect case badge.
- **Start:** `createState` stores `{ seed, generatorVersion, rounds: [] }` with a 128-bit random seed (32 hex characters). A cohort context starts a timed run: mode `standard`, `deadlineAt` = start + 180 s. A personal context starts practice: mode `practice`, no deadline.
- **Generator:** `generateRound({ seed, roundIndex })` builds each email from a SHA-256 based stream, so the same seed and index always give the same email. About 60% of rounds are genuine. Each round picks one of 20 scenarios (password expiry, sign-in alert, mailbox full, software update, device enrolment, vendor invoice, bank-detail change, payslip, expense claim, urgent executive payment, shared document, e-signature, calendar change, voicemail or fax, parcel delivery, subscription renewal, event or parking QR, benefits deadline, policy acknowledgement, staff survey) and the same scenario can arrive as a genuine email or a phish, so subjects and sender names never give the answer away. Genuine emails carry a safe-route sentence (for example "call the number on file") about half the time and phish never do. Phish types: lookalike domain, display-name spoof, reply-to mismatch, link-text mismatch, link-less payment-change (BEC), QR code, attachment. Difficulty tier is fixed by round: 1-4 tier 1, 5-9 tier 2, 10 and later tier 3. All domains are fictional `.example` hosts and links are inert text. Part IDs and round IDs are short random strings.
- **Action:** `triage-call` with `{ roundId, call: 'report' | 'trust', partId }`. `partId` is required for `report` and forbidden for `trust`. Any other field is rejected. The round ID must match the current email.
- **Hints (GUIDE-01):** practice runs only. Action `triage-hint` with `{ roundId }` (no other field). The server gives the next tier for the current round: tier 1 a general nudge ("Look closely at who really sent this."), tier 2 the concept to check ("Check whether the reply-to address differs from the sender."). Errors: `PHISH_HINT_UNAVAILABLE` (409, timed run), `PHISH_HINT_EXHAUSTED` (409, beyond tier 2), `PHISH_STALE_ROUND`, `PHISH_RUN_OVER`; ownership, revision and action limits come from the shared actions endpoint (no new route). Hints score nothing. State gains an optional `hint { roundId, tier }` (cleared by the next call) and each stored round an optional `hintTier` (default 0), so older attempts still read; the ruleset ID is unchanged. Public state adds `maxHintTier` (2 in practice, 0 timed) and `hint { tier, lines }` for the current email; `last` and `review` items carry `hintTier`. `triage/hints.js` holds the text per phish type; a phish hints at its own trick, and a genuine email hints at a trick drawn from its scenario's phish types that has a part to inspect in that email (a reply-to hint needs a reply-to, and so on), chosen by a seeded hash, so the wording and shape never reveal the verdict. Remaining statistical skew: a reply-to, link, QR or attachment nudge is somewhat more likely on a phish because genuine emails lack those parts more often.
- **Scoring:** a correct call scores 10, 20 or 30 by tier, plus 10 when a reported phish names one of its tell parts, multiplied by the streak before the call (x1 at 0-2, x2 at 3-5, x3 at 6 or more). Trusting a phish or reporting a legitimate email scores 0, is a mistake and resets the streak. Reporting a phish with the wrong part scores the call without the +10 and is not a mistake. Totals are derived from the stored rounds.
- **End conditions:** timed runs end at the deadline, the third mistake or 60 rounds; practice ends after 12 rounds. `canComplete` is true only then; before that complete returns 409. Actions after the end return `PHISH_RUN_OVER`.
- **Public state:** `{ mode, totalRounds, maxMistakes, roundsPlayed, serverNow, score, streak, mistakes, current, last }`, plus `review` once completed. `serverNow` lets the browser correct its countdown for a skewed device clock. `current` is the next email (no answer fields) and is `null` once the run is over. `last` is the previous round's outcome with the verdict, type, tell part IDs and explanation, revealed only after the call.
- **Errors:** shared attempt shape `{ error: { code, message }, requestId }`: `PHISH_INVALID_REQUEST` (400), `PHISH_INVALID_ACTION` (400), `PHISH_UNKNOWN_SELECTION` (400, part not in this email), `PHISH_STALE_ROUND` (409), `PHISH_RUN_OVER` (409), plus the shared `ATTEMPT_*` codes.
- **Ranking:** class-context standard-mode runs are `competitive`, so the leaderboard shows them as "Timed runs". Personal practice is not ranked. Strong runs tie at 1,000 on the Best board, because a saved score cannot pass the maximum. Rulesets never mix, so once a class completes a `phish-4` run its board shows `phish-4` only.

## phish-2 (legacy, not current)

`ruleset.js`, `policy.js`, `service.js` and `cases/` hold the inbox investigation: a random authored case of twenty emails, one `submit-verdict` action `{ selectedEmailId, evidenceIds }`, 100 points (60 for Patient Zero, 20 per correct clue), `competitive: false`. New attempts no longer use it. Keep these files while old results or unfinished `phish-2` runs may exist; the client shows such results as a score summary only. `server/tests/unit/phishing-post-mortem/case-integrity.test.js` still guards the case files.

## Changing the generator

Add a scenario as one entry in the `SCENARIOS` array in `generator/templates.js` (an id, 2-4 `phishTypes`, a `safeRoute` sentence and `safeNote`, and a `build(c, { verdict, phishType })` that returns the genuine email and lets `finish` turn it into the phish) and keep every domain on a fictional `.example` host. `generatorVersion` is stored on each run as a record only; `roundFor` always uses the one generator in the code. Open runs and saved reviews regenerate their emails from the stored seed, so a change that alters what an existing seed produces would make their explanations and topics contradict the stored scores. Make such a change only with a new `GENERATOR_VERSION` and a frozen copy of the old generator selected by that field. A golden hash in `server/tests/unit/phishing-post-mortem/triage-generator.test.js` fails on any such change; that file and `triage-ruleset.test.js` also cover determinism, content safety, the tier ramp, scoring and end conditions.
