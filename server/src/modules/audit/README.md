# Audit events

This module stores only the explicit event types allowlisted in [policy.js](policy.js): administrator bootstrap and provisioning, institution and class creation, renaming, deactivation and reactivation, instructor provisioning, cancellation and assignment, activation links, membership and class-code changes, account disabling and deletion, and student recovery. It does not add retroactive authentication, game, or general operational logging. Shared request-error behavior remains in `server/src/middleware/errors.js`.

`initializeAuditStorage(database)` creates the connection-bound `audit_events` collection and declared indexes. It does not seed, delete, synchronize, or drop data. The model uses `AuditEvent`, strict field handling, and disabled automatic collection/index creation.

`createAuditService(database, { now })` exposes `recordAuditEvent(input, { session })`. Current callers persist committed successes; refusals/failures use fixed caller guidance. The writer accepts only the declared event fields, owns `occurredAt` and `expiresAt`, set from the per-event retention map in [policy.js](policy.js) (`admin.account.delete` 180 days, every other event 90 days), and participates in each privileged caller's Mongo transaction. A write failure produces a generic safe error and aborts that mutation; callers must not report success without the event. Unknown fields and invalid values produce a generic safe error without echoing keys or values. `actorKind: 'operator'` requires `actorId: null`; user actors require a 24-character hexadecimal ID. [policy.js](policy.js) owns the shared event-type allowlist used by both the model and query validation; success/refused/failure are valid outcomes, with new callers requiring separate approval.

`listEvents(actor, query)` requires the current `admin:audit:read` capability before reading records. The `GET /api/admin/audit-events` route is session-protected and no-store. Only eventType/from/to/page/limit are accepted; repeated, unknown, object/operator and prototype-named inputs are rejected. Date filters are valid UTC ISO timestamps ending in Z, with optional one-to-three fractional digits, bounded to a non-future window of at most 180 days (the longest retention; rows of 90-day events simply expire earlier). Defaults are the last 90 days, page 1 and 20 rows; maximum page is 10,000 and maximum limit is 50. Expired records are excluded even before background TTL deletion. Results sort by newest event time and ID, and the response is `{ events, page, total }`. Each event returns only eventType/actorKind/actorId/targetId/scopeCohortId/outcome/occurredAt/requestId, plus targetRole/accountOutcome/reasonCategory/reasonNote on `admin.account.delete` rows; dates are ISO strings and IDs strings or permitted nulls. The list also adds `actorName`, `targetName` and `cohortName`: one lookup per page returns each record's current username or name, or null when it has gone, and these are never stored on the row. GET does not write audit records.

Audit events contain no free-text fields except one bounded exception: `reasonNote` (10 to 500 characters, entered by an administrator, accepted only on `admin.account.delete`, which also records `targetRole`, `accountOutcome` of `deleted` or `anonymised` and a fixed `reasonCategory`; the delete dialog warns not to enter names or emails). They contain no credentials, passwords, hashes, tokens, cookies, request bodies, stacks, or connection details. `requestId` is a UUID used only for correlation. Recovery, activation, admin and cohort events store the HTTP request's id, so a row can be matched to a response's `X-Request-ID` and a `request_failed` log line. The first-administrator bootstrap runs from a terminal with no HTTP request, so it generates its own. The writer does not generate authentication or game events; those require separate approved integration work.
